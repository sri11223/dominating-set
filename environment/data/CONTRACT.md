# Minimum dominating set contract

## Input

Each input is UTF-8 JSON with top-level keys `schema_version` and `instances`; `schema_version` is `minimum-dominating-set-v1`. Each instance has keys `n` and `edges`. `n` is the number of vertices; `edges` is an array of two-element arrays `[u, v]` with $0 \le u < v < n$ and no repeated edge. Vertex indices are arbitrary labels.

## Required answer

Write `solution.json` in the output directory; the answer file must be a regular file written directly into that directory, and every other entry the solver leaves in the output directory must be a regular file or a real subdirectory. It must be strict JSON with exactly the top-level key `instances`, an array with one entry per input instance, positionally paired with them: the entry at index $ i $ is the answer for the $ i $-th input instance, and the array must follow the input order. Each entry has exactly the key `dominating_set`, an array of distinct integers in $[0, n)$.

A set $S$ dominates a graph when every vertex is either in $S$ or adjacent to a vertex of $S$. For each instance, `dominating_set` must dominate the input graph, and its size must not exceed the minimum dominating-set size of that graph. Attaining the minimum is required: the minimum dominating-set size is the smallest size for which any dominating set exists, and the answer must have exactly that size.

## Input family and execution

The development instances under `/root/data/` are small sparse graphs with at most 100 vertices and at most 200 edges, and they include small representatives of both graph families: a relabelled 3-dimensional hypercube and a small hub/leaf graph. The same development-scale bounds apply to every further small instance set the solver is invoked on, and the minimum of each such set is attained by the maximum-gain greedy construction.

The solver must meet every requirement for each of four further instances drawn from the two families below.

* Two relabelled 15-dimensional hypercubes: 32768 vertices, 245760 edges, every vertex of degree 15. Vertex labels are arbitrary. Every vertex lies in exactly 16 closed neighbourhoods, so counting gives the lower bound 32768/16 = 2048, and a binary Hamming code of length 15 dominates with exactly 2048 vertices; the minimum is therefore exactly 2048. A greedy or local-search construction reaches about 3486 vertices.
* Two hub/leaf graphs: 30000 vertices and 40000 edges each, with 10000 hubs, each hub adjacent only to its own two private leaves, plus a sampled leaf layer in which one leaf of every hub carries no layer edge and the other carries a sampled 4-regular graph that never touches a hub. The 10000 closed neighbourhoods {hub, leaf, leaf} are pairwise disjoint and cover every vertex, so every dominating set has at least 10000 vertices and the hubs attain 10000; the minimum is exactly 10000. The leaf-layer edges are the family's separation gadget: they raise the layered leaves' closed gains above the hubs' and realize the standard maximum-gain greedy lower-bound construction for set cover and domination, so a maximum-gain greedy cover does not attain the bound (the shipped instances land at 12163 against the certified 10000) while the exact packing still certifies it. The solver must recover and certify the packing for each 30000-vertex, 40000-edge hub/leaf graph with 10000 hubs.

Each further input has at most 6 instances, each with at most 32768 nodes and at most 600000 edges, and the minimum dominating-set size is at most 32768. Vertex labels carry no information about the construction of an instance.

The solver is invoked as `python3 /root/candidate.py INPUT_JSON OUTPUT_DIRECTORY`; the public call starts in `/root/runtime/public` and the unseen call starts in `/root/runtime/heldout`. Each working directory and `OUTPUT_DIRECTORY` is fresh and writable. For execution, `/root/dominating_set_submission/solver.py` must exist as one self-contained nonempty regular Python source file of at most 4,000,000 bytes that does not depend on any sibling file in its submission directory. The solver must work when the exact bytes of `/root/dominating_set_submission/solver.py` are copied to `/root/candidate.py` and run as a single source file. The solver must derive its answer from `INPUT_JSON`, create `solution.json` in `OUTPUT_DIRECTORY`, and terminate with status zero. Each invocation receives a fresh per-invocation scratch area for incidental files (the process's `HOME` and `TMPDIR` point there); the shared system temporary and world-writable directories (`/tmp`, `/var/tmp`, `/dev/shm`, `/dev/mqueue`, `/run/lock`) are not writable by the solver, and no scratch state survives between invocations. The solver runs with no network access and an empty stdin, so inputs are available only through `INPUT_JSON`; `/root/data/` (including this document) is a development-time aid and is absent when the solver runs. The solver may use the standard library, numpy 2.2.6, scipy 1.15.3, and sympy 1.13.1; the numerical libraries are restricted to a single thread. Each invocation must use at most 4 CPUs, a virtual address space of 8,589,934,592 bytes (RLIMIT_AS, so sparse mappings and library reservations count against it) and 8192 MB of memory in its container, and aggregate CPU time is capped at 14,400 seconds, four times the wall-clock limit. The solver must derive answers from inputs across four invocations sharing the budget: the public call, the unseen call, and two calls on small instance sets generated at invocation time; each answer must be derived from the input it is given, not copied from another input's answer. Each invocation must finish within 3,600 seconds wall-clock, and the solver must complete all four invocations, including validation of their results, within a combined wall-clock limit of 14,400 seconds total. The solver must meet every stated requirement for both development and unseen invocations, not just a subset.
